# Env Vars Editing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Neil find, change, add and delete a service's variables in railway-tui, hold the
edits as pending changes on disk, review them, and deploy them one service at a time.

**Architecture:** The existing shape stays the same. `App::update` is pure and returns `Command`s.
The worker runs the commands and sends back `DataEvent`s, and `ui::draw` renders `App`. Pending
changes live in a new `src/pending.rs` model, which the app holds and the worker saves. All
writes go through a new `src/api/write.rs`, the only place mutations exist. The worker runs a
deploy as a sequence of steps and reports each one back, so the app can track which changes
were applied.

**Tech Stack:** Rust 1.96, ratatui 0.30, tokio, reqwest 0.12, graphql_client 0.14, serde/toml,
wiremock + tempfile for tests.

**Spec:** `docs/superpowers/specs/2026-10-28-env-vars-design.md`. It builds on
`docs/superpowers/specs/2026-10-28-railway-tui-design.md`.

## Global Constraints

- Exactly three mutations may exist: `variableCollectionUpsert`, `variableDelete` and
  `serviceInstanceRedeploy`. `tests/no_mutations.rs` enforces this.
- Mutations are sent only from `src/api/write.rs`, and only as a result of `y` on the deploy
  confirm prompt.
- No automated test writes to Railway. Every write path is tested with wiremock, and the live
  tests stay read-only. Neil runs the first real writes himself.
- Values never appear in logs, error messages, panics or `Debug` output. Only names may.
  `PendingVar` and every type holding a value implement `Debug` with the value redacted.
- Writes go through the same rate budget as reads. A write is refused without being sent while
  the budget is blocked.
- Writes are never resent automatically, including after a 401.
- Every colour comes from `app.theme()` (`src/theme.rs`).
- Every commit passes `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and
  `cargo test`. Each commit message ends with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- `/` searches names only, never values. It narrows the list live as you type, using the existing
  `filter_input`/`passes_filter` behaviour.

## Review Focus

1. **Unusual values:** an empty string, `=`, quotes, a newline, unicode, a 10 KB value. They must
   round-trip byte-for-byte through `pending.toml` and the upsert request body. This is pinned in
   Tasks 2 and 3.
2. **A corrupt or unreadable `pending.toml`:** pending edits are never silently discarded or
   overwritten. This is pinned in Task 3.
3. **Switching environment or project while editing or confirming:** a deploy always targets the
   environment and service of the pending group, never the one currently open. This is pinned in
   Task 8.
4. **A revealed value containing terminal escape sequences:** it is cleaned before drawing. This is
   pinned in Task 6.
5. **Pressing deploy while rate-limited:** nothing is sent, and the pending changes are untouched
   and still marked unapplied. This is pinned in Task 8.

### Task 3: Pending changes model and store

**Files:**
- Create: `src/pending.rs` (with unit tests)
- Modify: `src/lib.rs`

**Interfaces:**
- Produces:
  ```rust
  #[derive(Clone, PartialEq, Eq, Serialize, Deserialize)]
  pub enum Change { Set { value: String }, Delete }
  #[derive(Clone, PartialEq, Eq, Serialize, Deserialize)]
  pub struct PendingVar { pub change: Change, /// value on Railway when first edited; None = added
                          pub base: Option<String>, pub applied: bool }
  #[derive(Clone, Default, PartialEq, Eq, Serialize, Deserialize)]
  pub struct ServicePending { pub project_id: String, pub env_name: String, pub service_name: String,
                              pub vars: BTreeMap<String, PendingVar>, pub written_not_deployed: bool }
  #[derive(Clone, Default, PartialEq, Eq, Serialize, Deserialize)]
  pub struct Pending { pub envs: BTreeMap<String, BTreeMap<String, ServicePending>> } // env id → service id
  pub struct Target<'a> { pub project_id: &'a str, pub env_id: &'a str, pub env_name: &'a str,
                          pub service_id: &'a str, pub service_name: &'a str }
  impl Pending {
      pub fn set(&mut self, t: &Target, name: &str, value: String, current: Option<&str>);
      pub fn delete(&mut self, t: &Target, name: &str, current: Option<&str>);
      pub fn undo(&mut self, env_id: &str, service_id: &str, name: &str);
      pub fn discard(&mut self, env_id: &str, service_id: &str);
      pub fn service(&self, env_id: &str, service_id: &str) -> Option<&ServicePending>;
      pub fn count_for_project(&self, project_id: &str) -> usize;
  }
  pub fn pending_path(xdg_state_home: Option<&Path>, home: &Path) -> PathBuf; // …/railway-tui/pending.toml
  pub fn load_pending(path: &Path) -> Result<Pending, String>;
  pub fn save_pending(path: &Path, p: &Pending) -> io::Result<()>;
  ```
- Rules:
  - `base` is taken from `current` on the first edit only.
  - A `set` back to the base value removes the entry.
  - `delete` of an added variable (base `None`) removes the entry.
  - Empty services and environments are pruned.
  - `Debug` prints `<redacted>` in place of every value and base.
- `load_pending` behaviour:
  - A missing file gives `Ok(default)`.
  - A corrupt file is renamed to `pending.toml.corrupt` and returns
    `Err("pending changes file was unreadable; moved to <path>")`. It is never silently dropped.
- `save_pending` writes a temp file with mode `0600`, then renames it into place, the same way
  `save_remembered` does.

### Task 5: Editing: change, add, delete, undo, reveal, `$EDITOR`

**Files:**
- Modify: `src/app/mod.rs`, `src/app/keys.rs`, `src/main.rs`

**Interfaces:**
- Produces:
  - App field `pub var_input: Option<VarInput>`, where
    `pub struct VarInput { pub name: Option<String>, pub text: String }`. `name: None` means the
    name of a new variable is being typed.
  - `Command::EditExternal { name: String, initial: String }`, handled in the main loop and not
    the worker. It works like this:
    1. Leave the alternate screen and raw mode.
    2. Write `initial` to a `tempfile` with mode `0600`.
    3. Run `$VISUAL`, else `$EDITOR`, else `vi`.
    4. Read the file back and strip one trailing `\n`, then delete the file.
    5. Restore the terminal and deliver `DataEvent::Edited { name, result: Result<String, String> }`.
- Keys in the Variables view. These are the spec's calls:

  | Key | Action |
  | --- | --- |
  | `e` or `enter` | Edit the selected value inline. If the value contains `\n`, refuse with the message `multi-line value: press E to edit in $EDITOR`. |
  | `E` | `EditExternal` |
  | `a` | Prompt for a name, then a value. The name must match `^[A-Za-z_][A-Za-z0-9_]*$`, otherwise show a message. If the name already exists, it switches to editing that variable. |
  | `d` | Toggle delete |
  | `u` | Undo |
  | `r` | Toggle reveal of the selected value |
  | `R` | Toggle `reveal_all` |

- Editing behaviour:
  - Inline editing starts from the pending value if there is one, otherwise the current value.
  - Enter commits through `Pending::set`/`delete`, and Esc cancels.
  - Every change to `pending` emits `Command::SavePending`.
  - While `var_input` is open, keys go to it. Ctrl-C still quits.

### Task 8: Confirm and deploy

**Files:**
- Modify: `src/app/mod.rs`, `src/app/keys.rs`, `src/worker.rs`, `src/ui/pending.rs`,
  `src/ui/tests.rs`, `tests/api_http.rs` (worker-level wiremock tests if the worker tests live
  there; otherwise `src/worker.rs` tests)

**Interfaces:**
- Consumes: `write.rs` (Task 2), `Pending` (Task 3), `Confirm` (Task 7), `is_production` (Task 6).
- Produces:
  ```rust
  pub struct DeployConfirm { pub env_id: String, pub service_id: String, pub drift: Vec<String> } // names
  Command::DeployService { project_id: String, env_id: String, service_id: String,
                           upserts: Variables, deletes: Vec<String>, redeploy_only: bool }
  DataEvent::Deploy { env_id: String, service_id: String, step: DeployStep }
  pub enum DeployStep { Upserted, Deleted(String), Redeployed,
                        Failed { during: Phase, error: String, unknown: bool } }
  pub enum Phase { Upsert, Delete(String), Redeploy }
  ```
- Flow:
  1. `D` on a group (ids taken **from the group**, never from the open project or environment)
     sends `LoadVariables` for that group, with a flag `for_deploy`.
  2. The reply computes `drift`. A variable has drifted when its current value differs from its
     `base`, or when it was added and now exists.
  3. The reply opens `Confirm::Deploy`.
  4. The confirm overlay shows:
     - the env name (in `t.bad` for production);
     - the service;
     - every unapplied change, as on the review screen;
     - a `changed on Railway since your edit` line per drifted name;
     - the prompt `Deploy? y to confirm, any other key cancels`.
  5. `y` emits `DeployService` with the unapplied entries only. `redeploy_only` is set when every
     entry is applied and `written_not_deployed` is set.
- The worker runs the steps in order and stops at the first failure: upsert (skipped when
  `upserts` is empty), each delete, then redeploy. It sends a `Deploy` event after each step.
  The redeploy never runs after a failed write.
- How the app handles each event:
  - **`Upserted`:** mark the upserted entries applied and save.
  - **`Deleted(n)`:** mark `n` applied and save.
  - **All writes applied:** set `written_not_deployed` and save.
  - **`Redeployed`:** discard the group, save, show the message
    `deployed <service> to <env>`, and reload Services and variables if they are open.
  - **`Failed { unknown: false }`:** show `deploy failed during <phase>: <error>`. The pending
    entries stay as they are.
  - **`Failed { unknown: true }` during a write:** send `LoadVariables` with `for_reconcile`. The
    reply marks each entry applied when Railway now matches it: the value equals the new one, or a
    deleted variable is absent.
  - **`Failed { unknown: true }` during the redeploy:** show the message
    `redeploy outcome unknown — check the deployments view`.
